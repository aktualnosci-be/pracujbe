# Pracuj.be — kompletny audyt architektury, bezpieczeństwa i gotowości produkcyjnej

> **ARCHIWALNE — stan sprzed migracji na Railway (#27).** Raport opisuje repozytorium z 23.07.2026 (Supabase Auth/Storage/PostgREST, Vercel, Sentry); bieżąca architektura: [`CLAUDE.md`](../../CLAUDE.md), [`docs/ARCHITECTURE.md`](../ARCHITECTURE.md), [`docs/railway/README.md`](../railway/README.md).

**Data audytu:** 23 lipca 2026  
**Audytowany artefakt:** `pracujbe-claude-ci-selfhosted-setup-953u9x.zip`  
**Zakres:** kod aplikacji, dokumentacja, migracje i RLS, seed, testy, CI/CD oraz 7 makiet UI  
**Metoda:** analiza statyczna całego repozytorium, śledzenie ścieżek wywołań i polityk RLS, porównanie kodu ze schematem oraz dokumentacją kontraktową.  
**Ograniczenia wykonawcze:** instalacja npm została zablokowana przez brak rozwiązywania DNS do `registry.npmjs.org`; lokalnie nie były dostępne Supabase CLI, PostgreSQL ani Docker. Komendy zależne od `node_modules`, migracje, Lighthouse i testy z prawdziwą bazą oznaczono jako **niezweryfikowane**, a nie jako nieudane.

# 1. Executive summary

1. Pracuj.be **nie jest gotowe do produkcji**; obecny stan należy traktować jako fundament/scaffold wymagający zamknięcia krytycznych luk przed podłączeniem realnych użytkowników i danych.
2. Najpoważniejszy problem umożliwia zalogowanemu użytkownikowi dopisanie siebie jako `owner` do dowolnej istniejącej firmy, a następnie uzyskanie dostępu do danych tego tenant'a i zmiany statusu firmy.
3. Profile kandydatów są domyślnie wyszukiwalne, a anonimowa polityka RLS udostępnia całe wiersze, w tym lokalizację, mobilność, doświadczenie, dostępność i oczekiwania płacowe, zanim kandydat świadomie opublikuje profil.
4. Tabele `applications` i `offers` można modyfikować bez kontrolowanych operacji domenowych, co pozwala fałszować statusy, relacje, nadawcę, firmę i kandydata oraz omijać wymagane transakcje i historię.
5. Top-level `src/app/layout.tsx` nie renderuje wymaganych elementów `<html>` i `<body>`, więc kontrakt root layoutu Next.js jest naruszony; build nie mógł zostać uruchomiony z powodu ograniczenia sieciowego, ale wada jest jednoznaczna statycznie.
6. Callback Supabase Auth jest przechwytywany przez middleware `next-intl`, mimo że sam komentarz w handlerze wymaga wyłączenia `/auth`; potwierdzenia e-mail i reset hasła mogą kończyć się przekierowaniem na nieistniejącą trasę.
7. Właściciel profilu może zmienić własne pole `role` na `admin` lub `moderator`, ponieważ RLS chroni tylko `id`, a nie kolumny uprzywilejowane.
8. Warstwa odczytu ofert nie odpowiada znormalizowanemu schematowi SQL: pobiera wyłącznie `jobs.*`, ale mapuje kolumny firmy i tłumaczeń, których w tej tabeli nie ma; w środowisku z bazą treści będą puste lub błędne.
9. Wysyłka e-mail, kolejka, retry, webhooki i miejsca wywołań `resolveRecipientLocale` nie istnieją; poprawny util i komplet szablonów nie wystarczają do spełnienia inwariantu języka odbiorcy.
10. Tracking jest prawidłowo blokowany przed pierwszą zgodą, lecz późniejsze wycofanie zgody nie dezaktywuje już uruchomionych bibliotek GA/Meta ani ich cookies, a zgoda nie jest utrwalana po stronie serwera.
11. Mocne strony projektu to spójne 247 kluczy w czterech plikach językowych, brak wykrytych `any`/`@ts-ignore`, serwerowa walidacja Zod dla auth, neutralny reset hasła, RLS włączone na wszystkich 40 tabelach i brak importu service-role do komponentów klienckich.
12. Pięć najważniejszych ryzyk to: przejęcie tenant'a firmy, publiczny wyciek profili kandydatów, fałszowanie aplikacji/propozycji, niesprawny build/root layout oraz niesprawny callback uwierzytelniania.
13. Rekomendacja bramki produkcyjnej: najpierw usunąć wszystkie P0 i P1, dodać testy integracyjne RLS na prawdziwym Supabase, a następnie uzyskać zielone `lint`, `typecheck`, unit, build i e2e w kontrolowanym środowisku.

# 4. Szczegóły P0/P1

## P0-01 — przejęcie dowolnej firmy i obejście weryfikacji

### Dowód

```sql
-- supabase/migrations/0009_rls.sql:462-471
create policy companies_insert_authenticated on public.companies
  for insert to authenticated
  with check (auth.uid() is not null);

create policy companies_update_member on public.companies
  for update to authenticated
  using (public.is_company_member(id))
  with check (public.is_company_member(id));

-- :482-485
create policy company_members_insert on public.company_members
  for insert to authenticated
  with check (profile_id = auth.uid() or public.is_company_admin(company_id));
```

Tabela pozwala klientowi podać `companies.status`, `verified_at`, `verified_by` i `company_members.role` (`0002_core_tables.sql:80-105,127-139`). Komentarz o „pierwszym członku” nie jest egzekwowany przez warunek `NOT EXISTS`.

### Dlaczego problem jest realny

1. Zweryfikowane firmy są publicznie listowalne (`0009_rls.sql:452-455`), więc ich UUID nie jest sekretem.
2. Atakujący wstawia swój rekord członkostwa do wybranego UUID; warunek wymaga jedynie `profile_id=auth.uid()`.
3. Może od razu ustawić `role='owner'` i `is_active=true`.
4. Helper `is_company_member` widzi ten rekord i otwiera wszystkie polityki zależne od członkostwa.
5. Update firmy nie ogranicza kolumn, więc atakujący może zmienić status, dane weryfikacji lub soft-delete.

### Minimalna naprawa

- Drop `companies_insert_authenticated`, `companies_update_member` i bootstrapowej gałęzi `profile_id=auth.uid()`.
- Dodaj transakcyjną RPC tworzącą firmę oraz pierwszego właściciela; status zawsze ustawiaj w funkcji na `unverified`, niezależnie od payloadu.
- Osobna RPC `invite_company_member` wyłącznie dla aktywnego owner/admin.
- Weryfikację wykonuje wyłącznie service-role/admin z wpisem do `audit_logs`.

```sql
create or replace function public.create_company_with_owner(p_name text, p_slug text)
returns uuid
language plpgsql security definer set search_path=public
as $$
declare v_company_id uuid;
begin
  if auth.uid() is null then raise exception 'UNAUTHENTICATED'; end if;
  insert into companies(name, slug, status)
  values (p_name, p_slug, 'unverified')
  returning id into v_company_id;

  insert into company_members(company_id, profile_id, role, is_active, joined_at)
  values (v_company_id, auth.uid(), 'owner', true, now());
  return v_company_id;
end $$;

revoke insert, update on public.companies from authenticated;
revoke insert on public.company_members from authenticated;
grant execute on function public.create_company_with_owner(text,text) to authenticated;
```

### Dowód

3. `transition_application(application_id, target_status)` sprawdza aktora i allow-listę przejść.
4. W tej samej transakcji update + historia + notification + outbox email.
5. Dodać FK/trigger spójności firmy z ofertą.

Detail ma `APPLY_HREF='/login'` (`page.tsx:37-38`). Inwentaryzacja `src/app` nie wykazała page dla `/jobs`, `/login`, `/post-job`, `/how-it-works`, `/for-employers`, `/guides`.

### Naprawa

- Dodaj `pathnames` do konfiguracji next-intl i eksportuj typed route constants.
- Natychmiast ustaw Jobs=`/oferty-pracy`, login=`/logowanie`.
- Aplikuj: do czasu flow kieruj do `/logowanie?next=...` istniejącą trasą.
- Niezbudowane nav items ukryj albo daj prawdziwe landing pages przed publikacją.

## P1-11 — deploy może wyprzedzić czerwone CI

### Dowód

`ci.yml` i `deploy.yml` reagują osobno na `push` do main/develop. Deploy nie ma `needs`, nie wykonuje `npm run verify`, a Vercel build nie zastępuje lint/unit/e2e.

### Naprawa

Najprościej przenieść deploy do tego samego workflow po jobach jakości:

```yaml
deploy:
  needs: [build, e2e]
  if: github.event_name == 'push' && success()
```

Alternatywnie `workflow_run` po CI zakończonym `success`, checkout dokładnie `workflow_run.head_sha`. Włączyć required checks i zablokować direct push do main.

## P1-12 — staging nie ma pełnego noindex

### Dowód

`robots.ts` dla non-prod tylko zwraca `Disallow:/` (`16-28`). `sitemap.ts` bezwarunkowo tworzy pełny zestaw URL-i (`70-147`). `next.config.mjs` nie ustawia `X-Robots-Tag`, a locale layout nie daje globalnego robots metadata dla staging.

### Naprawa

- `sitemap()` zwraca `[]` w non-prod.
- W root metadata `robots: {index:false, follow:false, noarchive:true}` dla non-prod.
- `headers()` ustawia `X-Robots-Tag` dla wszystkich ścieżek preview/staging.
- Ochrona hasłem/Deployment Protection jako dodatkowa warstwa.

## P1-13 — platforma e-mail jest tylko scaffoldem

### Dowód

`resolveRecipientLocale` realizuje właściwy fallback (`src/lib/i18n/recipient-locale.ts:11-24`), a `renderEmail` obsługuje szablony. Grep nie znajduje żadnego wywołania Resend, enqueue ani zapisu `email_deliveries`; brak `src/lib/email` i `src/app/api`. Schemat ma `error_message`, ale nie `attempts`, `last_error`, `next_attempt_at` (`0006_messaging.sql:101-132`).

### Naprawa

- Outbox DB z `attempts`, `next_attempt_at`, `last_error`, lease/locked_at.
- `enqueueEmail` przyjmuje `recipientProfileId`, sam pobiera locale i e-mail.
- Worker atomowo claimuje batch, renderuje i wysyła z idempotency key.
- Webhook aktualizuje delivered/bounced.
- Testy: każdy typ × locale, fallback, retry, provider error nie usuwa aplikacji/oferty.

## P1-14 — dowolne dopisywanie uczestników rozmów

### Dowód

`conversation_members_insert` dopuszcza `profile_id=auth.uid()` **lub** creator/current member (`0009_rls.sql:728-735`) bez walidacji, czy dodawany profil jest stroną aplikacji/propozycji. Konwersację może utworzyć każdy z `created_by=auth.uid()` (`712-715`).

Jedna RPC `get_or_create_conversation(context_type, context_id)`:
